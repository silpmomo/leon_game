# leon_game 설계 — 모바일 웹 횡스크롤 액션 게임

- 작성일: 2026-08-21
- 저장소: `git@github.com:silpmomo/leon_game.git`
- 배포: GitHub Pages (`https://silpmomo.github.io/leon_game/`)

## 1. 목표

아이가 자기 폰 브라우저에서 링크 하나로 열어 끝까지 클리어할 수 있는 **1스테이지 완성형 마리오식 횡스크롤 게임**. 주인공은 제공된 사진 3장(`IMG_7508`·`IMG_7520`·`IMG_7550`)을 근거로 만든 캐릭터이고, 적과 아이템도 같은 사진에서 소재를 가져온다.

성공 기준:

1. 아이폰 Safari 가로모드에서 화면 컨트롤러만으로 처음부터 끝까지 플레이 가능
2. 프레임 드롭 없이 60fps 유지, 초기 로드 100KB 이하
3. 물리·규칙이 단위 테스트로 고정되어 조작감 회귀가 잡힘
4. 레벨 데이터를 손으로 고쳐도 클리어 불가 스테이지가 만들어지지 않음(검증 테스트)

## 3. 아키텍처

### 3.1 원칙 — 순수 코어 / 더러운 껍질

물리·규칙·충돌을 브라우저를 모르는 순수 함수로 격리한다. `canvas`·`window`·`Touch`를 import하는 파일과 그렇지 않은 파일을 디렉터리로 갈라놓는다.

```
순수 레이어 (브라우저 없이 테스트)      껍질 레이어 (브라우저 의존)
  engine/  물리·AABB·카메라       ←──   render/  캔버스 드로우
  game/    규칙·상태머신           ←──   ui/      버튼·오버레이
  world/   타일맵·엔티티           ←──   core/    입력·오디오·루프
        ↑ import는 이 방향으로만. 역방향은 lint로 차단
```

`eslint` `import/no-restricted-paths`로 `engine/`·`game/`·`world/`에서 `render/`·`ui/`·`core/` import를 금지한다.

### 3.3 데이터 흐름 — 한 프레임

```
터치/키 이벤트  →  input.ts  →  InputState { left, right, jump, jumpHeldMs }
                                      │
loop.ts  고정 dt = 1/60초 · 최대 5프레임 캐치업
                                      ▼
   update(state, input, dt) ── 전부 순수 함수, 이 순서 고정
     1. player.ts     입력 → 가속·점프 의도
     2. physics.ts    중력 → x축 이동·해소 → y축 이동·해소 (축 분리)
     3. entities.ts   적 이동·방향 전환·아이템 궤적
     4. rules.ts      밟기/피격/코인/파워업/골 판정
     5. camera.ts     플레이어 추적 → 레벨 경계 클램프
                                      ▼  새 GameState
   render(state)  ────────►  캔버스 (배경 → 타일 → 엔티티 → 플레이어 → HUD → 버튼)
```

`GameState` 하나가 단일 진리원천이고, 렌더러는 읽기만 한다. 부작용으로 상태를 고치는 경로가 없으므로 화면과 실제 상태가 어긋나는 버그가 구조적으로 발생하지 않는다.

**고정 timestep을 쓰는 이유**: 가변 dt면 기기 성능에 따라 점프 높이가 달라진다. 아이 폰과 개발 노트북에서 점프 거리가 같아야 레벨 설계가 성립한다.

## 4. 물리 · 조작감

### 4.1 해상도와 타일

- 타일 16px, 논리 화면 **416 × 192px** (26 × 12 타일)
- 캔버스는 **정수 배율만** (2배·3배). 남는 여백은 레터박스
- 아이폰 가로 844×390 기준 2배 = 832×384, 여백 6px·12px

원작이 세로 15타일인데 12타일로 줄인 이유: 폰 가로모드는 세로가 짧다. 대신 가로가 26타일(원작 16타일)이 되어 앞쪽 지형을 멀리 본다. 터치 조작은 반응이 한 박자 늦으므로 예측 가시거리가 중요하다.

### 4.2 물리 상수 (초기값, 전부 튜닝 대상 — `engine/tuning.ts`)

| 항목 | 값 |
|---|---|
| 걷기 최고속도 | 90 px/s |
| 달리기 최고속도 | 150 px/s (버튼 유지 1.2초 후 도달) |
| 지상 가속 | 300 px/s² |
| 감속 (입력 없음) | 450 px/s² |
| 방향 전환 감속 (스키드) | 900 px/s² |
| 공중 가속 | 200 px/s² |
| 점프 초기속도 | −320 px/s |
| 상승 중력 (버튼 유지) | 700 px/s² |
| 하강 중력 | 1400 px/s² |
| 최대 낙하속도 | 400 px/s |
| 코요테 타임 | 80 ms |
| 점프 버퍼 | 120 ms |
| 코너 보정 | 3 px |
| 밟기 튕김 | −180 px/s (점프 유지 시 −280) |

파생 계산 (검증 테스트가 이 식을 그대로 쓴다):

- 최고 점프 높이 = `320² / (2 × 700)` = **73px ≈ 4.6타일**
- 체공 시간 = 상승 `320/700 = 0.457s` + 하강 `√(2×73/1400) = 0.323s` = **0.78s**
- 걷기 점프 도달 거리 = `90 × 0.78` = **70px ≈ 4.4타일**
- 달리기 점프 도달 거리 = `150 × 0.78` = **117px ≈ 7.3타일**

따라서 통과 가능한 구덩이 폭은 걷기 4타일 이하, 달리기 **6타일 이하**(96px, 여유 21px)다.

**최대 낙하속도 400의 역할**: 한 프레임 이동량이 `400/60 = 6.7px`로 타일 16px보다 작다. 빠르게 떨어져도 바닥을 관통하는 터널링이 구조적으로 불가능하다.

### 4.3 조작감을 만드는 장치

1. **가변 점프** — 버튼을 떼는 순간 상승 중력 2배. 짧게 1.5타일, 길게 4.6타일
2. **코요테 타임 80ms** — 발판에서 막 떨어진 직후에도 점프 성립
3. **점프 버퍼 120ms** — 착지 직전 입력을 기억해 착지 즉시 발동
4. **속도 보존** — 달리던 속도가 점프에 실림. 긴 구덩이가 "달려서 넘는" 구간이 된다
5. **밟기 튕김** — 점프 버튼을 누른 상태면 더 높이 튕겨 연속 밟기 콤보 가능
6. **코너 보정 3px** — 머리가 블록 모서리에 살짝 걸리면 옆으로 밀어냄
7. **좁은 히트박스** — 스프라이트보다 좁아 "닿은 것 같은데 안 죽음"

2·3·6은 없으면 조작이 뻣뻣해지고, 플레이어는 그 이유를 설명하지 못한다. 아이용에서 특히 중요하다.

### 4.4 충돌 해소

```
1. x축만 이동  → 겹친 타일 검사 → 벽이면 x를 타일 경계로 밀어냄, vx = 0
2. y축만 이동  → 겹친 타일 검사 → 바닥이면 y 보정 + onGround = true
                                → 천장이면 vy = 0 + 블록 치기 발동
```

- **축 분리**가 핵심. x·y를 동시에 해소하면 모서리에서 밀어낼 방향이 모호해져 벽에 붙어 떠는 버그가 생긴다
- 타일 조회는 AABB가 겹치는 격자 범위만 순회 → 프레임당 4~6칸. 브로드페이즈 불필요
- **이동발판**은 아래→위 단방향 통과. 위에 서면 발판 속도가 플레이어에 더해진다

### 4.5 히트박스

| 대상 | 스프라이트 | 히트박스 |
|---|---|---|
| 주인공 (작을 때) | 16 × 24 | 11 × 21 |
| 주인공 (클 때) | 20 × 32 | 13 × 29 |
| 브로콜리 | 14 × 14 | 12 × 12 |
| 미역국 | 16 × 14 | 14 × 12 |
| 악어 | 28 × 12 | 26 × 10 |
| 복숭아 · 축구공 | 14 × 14 · 12 × 12 | 동일 |

얼굴이 사진이라 머리 비중이 커서 2등신이 되고 세로가 길다. 작은 상태 높이가 1.3타일이므로 **통과 통로 최소 높이는 2타일**이다. 마리오 1-1에도 1타일 통로는 없으므로 설계상 손실은 없다. 레벨 검증 테스트가 이를 자동 확인한다.

### 4.6 적 판정 — 밟기 vs 피격

```
밟기 성립:  플레이어 vy > 0 (하강 중)  AND  플레이어 발 < 적 상단 + 4px
그 외 접촉 →  피격
```

여유 4px이 없으면 "밟았는데 죽었어"가 반복된다. **악어는 밟기 불가** — 위에서 닿아도 피격이며, 등의 가시로 시각적으로 구분된다.

### 4.7 튜닝 방법

상수 전체가 `engine/tuning.ts` 한 파일에 있다. 개발 빌드에서 `?debug=1`을 붙이면 슬라이더 패널이 떠서 실기에서 직접 조정하고, 확정값을 파일에 반영한다. 같은 플래그로 히트박스·타일 격자·속도 벡터 오버레이가 켜진다.

## 5. 게임 규칙

### 5.1 플레이어 상태

3단계: `small` → `big` → `big+ball`

- 복숭아 획득: `small` → `big` (몸 커짐)
- 축구공 획득: `big` → `big+ball` (`small`에서 먹으면 `big`으로만)
- 피격: 한 단계 하락 + 무적 1.5초(깜빡임). `small`에서 피격 시 사망
- 낙하사: 레벨 바닥 아래 32px 통과 시 (무적 무관)

### 5.2 적 3종

| 적 | 행동 | 밟기 | 처리법 |
|---|---|---|---|
| 브로콜리 | 40 px/s 직진, 벽에서 방향 전환, 절벽에서는 떨어짐 | 가능 | 밟기 · 축구공 · 아래에서 블록 치기 |
| 미역국 | 제자리에서 1.4초 주기 점프 (−260 px/s) | 가능 (공중에 떠 있을 때도 성립) | 밟기 · 축구공 |
| 악어 | 플레이어가 8타일 내 진입 시 90 px/s 돌진, 벽에서 방향 전환 | **불가 (피격)** | 축구공 2발 · 아래에서 블록 치기 · 뛰어넘기 |

아래에서 블록을 치면 그 블록 위의 적은 뒤집혀 제거된다.

### 5.3 아이템 · 블록

- **코인**: 200점. 100개당 목숨 +1 (연습 모드는 목숨이 무한이므로 도전 모드에서만 의미가 있다)
- **복숭아**: `?` 블록에서 나와 40 px/s로 굴러감 (마리오 버섯과 동일)
- **축구공**: 수평 120 px/s + 포물선 바운스, 벽 3회 바운스 후 소멸, 동시 최대 2개. 악어는 2발로 제거된다.
  발사 입력은 **조건부 4번째 버튼**으로 한다 — 평소에는 버튼이 3개이고, `big+ball` 상태일 때만 점프 버튼 왼쪽에 발사 버튼이 나타난다(등장 시 확대 애니메이션). 사용자가 고른 3버튼 구성을 평시에 유지하면서, 버튼이 새로 생기는 것 자체가 "새 능력을 얻었다"는 피드백이 된다. ◀/▶ 더블탭 방식은 달리기 자동 가속(버튼 유지)과 충돌하므로 쓰지 않는다
- **블록**: 땅(파괴 불가) · 벽돌(치면 부서짐, 일부는 코인 숨김) · `?` 블록(코인/복숭아/축구공, 치면 빈 블록) · 단단블록(튕김만) · 파이프(올라서기, 진입 없음) · 이동발판

`?` 블록 내용은 타일 문자로 구분한다(`?` 코인 / `@` 복숭아 / `*` 축구공).

### 5.4 모드

| | 연습 | 도전 |
|---|---|---|
| 목숨 | 무한 | 3개 |
| 사망 시 | 직전 체크포인트에서 부활 | 스테이지 처음부터 |
| 목숨 소진 | 해당 없음 | 게임오버 → 타이틀 |

### 5.5 점수

- 코인 200 · 적 밟기 100 (연속 콤보 100→200→400→800) · 깃대 높이 보너스 최대 5000 · 남은 시간 ×50 (도전 모드)

플레이어를 화면 가로 40% 지점에 두고 추적하며, 레벨 경계로 클램프한다. **왼쪽 스크롤 잠금은 두지 않는다** — 원작은 되돌아가기를 막지만, 아이가 실수로 왼쪽으로 갔을 때 벽에 막히는 경험이 답답하므로 양방향 자유 스크롤로 한다.

## 6. 스테이지 1-1

### 6.1 구간 설계

원칙: **새 요소는 안전한 곳에서 먼저 소개하고, 위험은 다음 구간에 붙인다.** 각 구간은 정확히 하나만 가르친다.

| 구간 | 타일 | 가르치는 것 | 구성 |
|---|---|---|---|
| A | 0–24 | 걷기 · 첫 점프 | 평지. 코인 3개를 점프 한 번 높이에 배치. 브로콜리 1 (화면 끝에서 느리게 접근) |
| B | 24–48 | 블록 치기 · 파워업 | 벽돌 + `@`(복숭아) + `?`(코인). 파워업을 먹은 채 다음 구간 진입 유도. 브로콜리 1 |
| C | 48–70 | 올라서기 · 높이차 | 파이프 2타일 → 4타일. 사이에 브로콜리 1을 두어 파이프 위 피신을 발견하게 함 |
| D | 70–92 | 구덩이 · 달리기 점프 | 구덩이 3타일(48px, 걷기로 넘김) → **5타일**(80px, 걷기 도달 70px을 넘어 달려야 함). **적 0마리** |
| E | 92–118 | 튀는 적 · 축구공 | 공중 벽돌 다리(우회로) + 미역국 2 + `*`(축구공) |
| F | 118–142 | 밟을 수 없는 적 | 악어 1. 천장 단단블록으로 통로를 좁혀 뛰어넘기를 "어렵지만 가능"하게 조절 |
| G | 142–168 | 이동발판 | 낙하 구간 위 좌우 발판 → 상하 발판 |
| H | 168–190 | 총복습 | 브로콜리 3 + 악어 1 + 계단(연속 밟기 가능) |
| I | 190–200 | 골 | 적 0. 깃대 슬라이딩, 잡은 높이에 따라 보너스. 성 진입 후 결과 화면 |

D구간에 적을 두지 않은 것은 의도적이다. "계속 누르면 빨라진다"를 배우는 자리에 다른 방해물이 있으면 아이가 원인을 혼동한다.

체크포인트: 타일 70 · 118 · 142 · 168 (각 구간 입구).

### 6.2 레벨 데이터 포맷 — 아스키 격자

타일 하나를 글자 하나로 적는다. 12줄 × 200자.

```json
{
  "name": "1-1",  "width": 200,  "height": 12,
  "spawn": { "x": 3,  "y": 9 },
  "goal":  { "x": 190, "flagTop": 4 },
  "tiles": [
    "........................................",
    "........................................",
    "..........................o.o.o.........",
    "........................................",
    "..................BB@B?.................",
    "........................................",
    "........................................",
    ".............................p p........",
    ".............................| |........",
    "........................................",
    "########################.....###########",
    "########################.....###########"
  ],
  "entities": [
    { "type": "broccoli",  "x": 22,  "y": 9,  "dir": -1 },
    { "type": "soup",      "x": 101, "y": 9 },
    { "type": "crocodile", "x": 128, "y": 9,  "dir": -1 },

    { "type": "platform",  "x": 158, "y": 5, "axis": "y", "range": 3, "speed": 30 }
  ],
  "checkpoints": [ 70, 118, 142, 168 ]
}
```

타일 문자:

| 문자 | 의미 | 문자 | 의미 |
|---|---|---|---|
| `.` | 빈칸 | `#` | 땅 (파괴 불가) |
| `B` | 벽돌 | `b` | 벽돌 + 코인 숨김 |
| `?` | `?` 블록 → 코인 | `@` | `?` 블록 → 복숭아 |
| `*` | `?` 블록 → 축구공 | `H` | 단단블록 (튕김만) |
| `p` / `|` | 파이프 상단 / 몸통 | `o` | 코인 (공중) |

적·이동발판만 `entities` 배열로 뺀 이유는 방향·이동범위·속도 같은 파라미터가 필요하기 때문이다.

**레벨 에디터는 만들지 않는다.** 이 포맷은 메모장에서 편집 가능하고 git diff에 지형 변화가 그림처럼 보인다. 에디터는 YAGNI.

### 6.3 레벨 검증 규칙 (`levels/schema.ts`, 테스트로 실행)

1. 모든 행 길이 = `width`, 행 수 = `height`
2. 미정의 문자 없음
3. `spawn`이 빈칸이고 바로 아래가 땅
4. **모든 구덩이 폭 ≤ 6타일** — `tuning.ts` 상수로 4.2절 식을 계산해 도출하며, 상수를 바꾸면 한계값도 따라 바뀐다
5. 모든 통과 통로 높이 ≥ 2타일
6. 모든 `checkpoints` 좌표가 땅 위의 빈칸
7. `goal.x` + 깃대가 레벨 범위 안

4번이 실질적으로 유용하다. D구간 구덩이를 8타일로 늘리면 "8타일(128px)은 달리기 도달 거리 117px을 초과한다"고 테스트가 알려준다.

## 7. 입력 · UI

### 7.1 컨트롤러

- **3버튼**: 좌하단 `◀`(11% 폭) `▶`(11%), 우하단 `점프`(15%) — 논리 좌표 기준, 하단 여백 6%
- **조건부 4번째 버튼**: `big+ball` 상태에서만 점프 버튼 왼쪽에 `발사`(12%)가 등장. 상태를 잃으면 사라진다
- 불투명도 42%, 캔버스에 직접 그림 (DOM 요소 아님 — 레이어 순서·스케일 일관성)
- **히트박스는 보이는 원보다 20% 크게**
- 누르는 순간 살짝 확대 + `navigator.vibrate(10)` (지원 기기만)
- `pointerId`별로 상태 추적 → 멀티터치·버튼 밖 슬라이드 정상 처리
- 좌우 동시 입력은 **나중에 누른 쪽 우선**
- `safe-area-inset` 회피, `touch-action: none`으로 확대·스크롤 차단
- 키보드도 지원 (개발용): ← → · Space/↑

**레벨 디자인 제약**: 좌우 하단 코너는 버튼이 겹치는 영역이므로, 구덩이 입구·중요 아이템을 그 위치에 두지 않는다.

## 10. 테스트 전략 (vitest)

순수 레이어만 테스트한다. 목적은 조작감·규칙의 회귀 방지다.

| 대상 | 검증 |
|---|---|
| `aabb` | 겹침·스윕 경계 케이스 (정확히 맞닿음, 0폭) |
| `physics` | 최대 낙하속도로 바닥 통과 없음 · 벽에 붙어도 위치 떨림 없음 · 코너 보정 3px |

| `camera` | 레벨 경계 클램프 |
| `score` | 콤보·깃대 보너스·시간 보너스 |

## 14. 후속 판단 사항

- 물리 상수는 초기값이다. 아이가 실기에서 만져본 뒤 조정한다. 특히 **달리기 자동 가속 1.2초**와 **최고 점프 4.6타일**은 실제 플레이 없이 확정할 수 없다
- 조건부 발사 버튼이 갑자기 나타났을 때 아이가 알아채는지 실기 확인이 필요하다. 못 알아채면 등장 시 짧은 화살표 힌트를 덧붙인다
- 얼굴 크롭 좌표는 `IMG_7520`을 1순위로 하되, 32px·10색 결과를 보고 다른 사진이 더 나으면 교체한다
